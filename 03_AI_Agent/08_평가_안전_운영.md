# 에이전트 평가 · 안전 · 운영

## 1. 왜 평가(Eval)가 핵심인가
- LLM 출력은 비결정적 → "몇 번 써보니 괜찮더라"는 위험
- 프롬프트/모델/도구를 바꿀 때마다 **회귀(regression)**를 잡아야 함
- **평가셋이 곧 제품 사양서**

## 2. 평가 방법
| 방법 | 설명 | 장단점 |
|---|---|---|
| 코드 기반 채점 | 정답 일치, 정규식, JSON 스키마, 단위 테스트 통과 | 빠르고 정확, 열린 답엔 한계 |
| **LLM-as-a-judge** | 다른 LLM이 기준(루브릭)에 따라 채점 | 확장성↑, 편향 주의 → 사람 평가와 일치도 확인 |
| 사람 평가 | 전문가 검토, A/B 테스트 | 가장 신뢰, 비쌈 |

## 3. 에이전트 평가 관점
- **최종 결과**: 과제를 성공했는가? (환경 상태 확인: 파일이 생겼나, 테스트가 통과하나)
- **경로(trajectory)**: 적절한 도구를 적절한 순서로? 불필요한 단계는?
- **효율**: 단계 수, 토큰, 비용, 시간
- **안전**: 금지 행동을 했는가, 승인 없이 부작용을 일으켰는가
- 비결정성 → 같은 과제를 **여러 번** 실행해 성공률(pass@k) 측정

## 4. 평가셋 만들기
1. 실제 사용 사례에서 20~50개로 시작 (작아도 OK, 시작이 중요)
2. 쉬운/어려운/엣지 케이스/적대적 케이스 섞기
3. 실패 사례가 나올 때마다 평가셋에 추가
4. 성공 기준을 구체적으로 (루브릭)

## 5. 보안 위협

### 프롬프트 인젝션 (Prompt Injection)
- **직접**: 사용자가 "이전 지시 무시해"
- **간접**: 에이전트가 읽은 웹페이지·이메일·문서 안에 숨은 지시 → 에이전트를 조종
- 에이전트가 **도구 + 민감 데이터 + 외부 통신**을 함께 가지면 특히 위험 (데이터 유출 경로)

### 방어 (단일 해법은 없음 → 다층 방어)
- 외부 데이터는 **명령이 아닌 데이터**로 취급하도록 설계·프롬프트
- **최소 권한**: 필요한 도구·범위만
- 부작용 있는 행동 전 **사람 승인**
- 샌드박스 실행, 네트워크 제한(허용 목록)
- 입력/출력 필터, 민감 정보 마스킹
- 도구 결과와 사용자 지시를 구분되게 표시

### 기타 위험
- 과도한 자율성으로 인한 파괴적 행동 (파일 삭제, 대량 메일)
- 환각된 도구 인자 / 존재하지 않는 API
- 비밀키 노출, 개인정보 처리
- 비용 폭주 (무한 루프)

## 6. 운영 (LLMOps / AgentOps)
- **관측성(Tracing)**: 모든 LLM 호출·도구 호출·입출력·토큰·지연을 기록
- **비용 최적화**:
  - 작업 난이도별 모델 라우팅 (작은 모델 우선)
  - **프롬프트 캐싱** (긴 시스템 프롬프트/문서 재사용)
  - 배치 API, 출력 길이 제한, 불필요한 컨텍스트 제거
- **지연 최적화**: 스트리밍, 병렬 도구 호출, 캐시
- **신뢰성**: 재시도(지수 백오프), 폴백 모델, 타임아웃, 레이트리밋 처리
- **버전 관리**: 프롬프트·도구 정의도 코드처럼 버전 관리 + 평가 후 배포
- **사용자 피드백 수집** → 평가셋 확장 → 개선 루프

## 7. 배포 전 체크리스트
- [ ] 평가셋에서 목표 성공률 달성
- [ ] 최대 단계·비용·시간 제한 설정
- [ ] 부작용 행동에 승인 절차
- [ ] 인젝션 테스트 케이스 통과
- [ ] 트레이싱·알림 설정
- [ ] 실패 시 사람에게 넘기는 경로(escalation)

- 결과·경로·안전을 따로 채점하고 케이스마다 20번 실행해 성공률을 측정하는 평가 하네스를 만듦.

- pass@3(3번 중 1번 성공)과 pass^3(3번 모두 성공)의 차이가 큼 → 실서비스 신뢰성은 pass^k로 봐야 함.
