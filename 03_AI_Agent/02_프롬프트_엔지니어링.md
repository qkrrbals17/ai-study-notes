# 프롬프트 엔지니어링 (Prompt Engineering)

에이전트 성능의 기초. 최근엔 **컨텍스트 엔지니어링**(모델에게 어떤 정보를 언제 얼마나 줄지 설계)으로 확장되는 추세.

## 1. 기본 원칙
1. **명확하고 구체적으로**: "새로 온 똑똑한 동료에게 설명하듯" 배경·목적·제약을 다 적는다
2. **역할과 맥락 제공**: 시스템 프롬프트로 역할, 대상 독자, 톤
3. **원하는 출력 형식 명시**: 길이, 구조, JSON 스키마
4. **예시 제공 (Few-shot)**: 좋은 예/나쁜 예
5. **하지 말라보다 하라를**: "마크다운 쓰지 마" → "평문 문단으로 작성해"
6. **이유를 설명**: 규칙의 이유를 알려주면 모델이 더 잘 일반화
7. **복잡한 작업은 분해**

## 2. 프롬프트 구조 예시
```
[시스템]
당신은 핀테크 회사의 시니어 데이터 분석가입니다.
독자는 비전공 경영진이므로 전문 용어는 풀어서 설명하세요.

[사용자]
<context>
{분기 매출 데이터}
</context>

<task>
위 데이터로 3분기 실적 요약을 작성하세요.
</task>

<format>
- 핵심 요약 3문장
- 주요 지표 표
- 위험 요인 2가지
</format>
```
→ XML 태그 등으로 **데이터와 지시를 구분**하면 혼동·인젝션 위험이 줄어듦

## 3. 주요 기법
| 기법 | 설명 | 언제 |
|---|---|---|
| Zero-shot | 지시만 | 간단한 작업 |
| Few-shot | 입력-출력 예시 몇 개 | 형식·스타일 고정 |
| **Chain-of-Thought (CoT)** | "단계별로 생각해" / 추론 과정 출력 | 수학·논리·다단계 |
| Self-consistency | 여러 번 추론 후 다수결 | 정답이 명확한 문제 |
| 프롬프트 체이닝 | 작업을 여러 호출로 분리 | 복잡한 파이프라인 |
| Prefill | 응답 시작 부분을 미리 채움 | 형식 강제 |
| 역할 프롬프트 | 전문가 페르소나 | 도메인 톤 |

※ 최근 "추론(thinking) 모델"은 내부적으로 길게 생각하므로, 지나치게 세세한 CoT 지시보다 **목표와 기준을 명확히** 주는 편이 나은 경우가 많다.

## 4. 구조화된 출력 (Structured Output)
에이전트/시스템 연동엔 필수
- JSON 스키마 지정 + API의 구조화 출력 기능 사용
- Pydantic으로 검증, 실패 시 재시도

```python
from pydantic import BaseModel
class Ticket(BaseModel):
    category: str
    urgency: int   # 1~5
    summary: str
# LLM 출력 → Ticket.model_validate_json(output)
```

## 5. 컨텍스트 엔지니어링
- 컨텍스트 창은 유한한 자원 → **관련성 높은 정보만**
- 긴 문서는 앞쪽에, 질문은 뒤쪽에 두면 효과적인 경우가 많음
- 오래된 도구 결과는 요약·삭제 (compaction)
- 필요할 때 가져오기(just-in-time retrieval) vs 미리 다 넣기

## 6. 프롬프트 개선 프로세스
1. 성공 기준 정의 → 2. 테스트 케이스(평가셋) 만들기 → 3. 초안 작성
→ 4. 실행·실패 사례 분석 → 5. 수정 → 반복
**감이 아니라 평가셋으로 개선**한다 → [08_평가_안전_운영.md](08_평가_안전_운영.md)
